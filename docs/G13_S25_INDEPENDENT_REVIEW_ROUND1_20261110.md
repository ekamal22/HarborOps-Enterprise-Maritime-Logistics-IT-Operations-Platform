## Findings, most severe first

### F1 (High, blocks PASS): four-principal and skewed-scale evidence is not at 170,000 rows
- `M13ScaleLoadTests.cs:286` and `:307` build the 170k tenant from `Draft` shipments, then flip 60,000 to `Cancelled` by UPDATE (no status-change rows). The asserted result is only D01/K01/K02/K04 (`:356-361`, 450,006 members). No shipment is Booked/InTransit/Arrived/Completed, there are no `shipment_exception_evaluations`, no exceptions and no history rows. The expensive CTEs (`events`, `evaluated`, `quality`, K03-K14 branches, `OperationalKpiStore.cs:322-482`) see near-empty inputs. The p50 9,605 ms / p95 10,430 ms (`g13-scale-c1/scale.log`) is therefore a floor for the Draft/Cancelled path, not for a realistic tenant.
- `M13_VERIFICATION_PLAN.md` S20 requires "170,000-row skewed-tenant data ... and concurrent load"; section 5 lists "Measured 170k-tenant ... concurrent load envelope" as an acceptance blocker; plan section 4 asks for "history/exception fanout". The 170k test uses one principal. The only four-principal test (`M13ConcurrentAcceptanceTests.cs:42-47`) uses 5,002 Draft shipments and finished in 1,266 ms.
- Source inference (NOT executed, treat as unverified): `BuildOnceAsync` holds a tenant-wide `pg_advisory_lock` for the whole build (`OperationalKpiStore.cs:176-184`) with `CommandTimeout = 15` on the lock wait (`:178`). At about 10 s per 170k build, the third and fourth simultaneous builders would wait about 20 s and be expected to time out, returning 503 `report_dependency_unavailable` (`OperationalKpiEndpoints.cs:185`). That is bounded and fail-closed, but it is the behavior G13-S20-A06 exists to characterize, and no evidence shows it.
- G13-S20-A06 is literally satisfied (four principals, concurrently, 5k rows); G13-S20-A02/A03 are literally satisfied (30 samples at 170k). The plan's intent is not.
- To close: run four concurrent principals against a 170k tenant that has realistic status spread, status-change history and exception evaluations (at least tens of thousands of non-Draft shipments with 4 rule rows each); record p50/p95 and the outcome of requests 3 and 4; either show success inside the budget or record an explicit policy decision that 503 is the approved behavior for concurrent builders.

### F2 (Medium): two of 24 source mutants are killed by a database constraint, not by the named protection
- `k03-duplicate-status-history` (`scripts/g13-mutation-campaign.py:77-88`): the mutant appends a duplicate `UNION ALL`. Log shows `23505 duplicate key ... operational_kpi_members_pkey`, HTTP 503, test fails at `Json()` status check. It does not remove the `DISTINCT ON (shipment_id,to_status)` de-duplication in `events` (`OperationalKpiStore.cs:323-329`), which is the protection "duplicate status history" implies.
- `tenant-materialization-scope-removed` (`:22-25`): log shows `23503 ... fk_m13_member_shipment`, HTTP 503. Foreign-tenant shipments are blocked by the composite FK, so the named WHERE clause is never shown to matter to a content assertion. This is useful defense-in-depth evidence, but it is not the claimed kill.
- Cause: the `KILLED` rule (`:264-266`) accepts any nonzero exit plus the test name and "Failed" in the output; it does not check the failure reason.
- The other 22 mutants fail on content assertions (wrong counts, wrong status, wrong boundary), which is the right reason. SQL security mutants 1-4 fail on `Expected 0/Actual 1`, `Actual 6`, and the "must remain unable to view" assertion: valid.
- To close: replace the K03 mutant with one that removes the `DISTINCT ON`/first-event rule and fails on a count; add a tenant-scope mutant that survives the FK (or state plainly that the FK is the control).

### F3 (Medium): "no business record removed" and "no counts" are weak negative witnesses
- G13-S19-A08 ("without removing any ... business record"): `M13TenantCapacityAcceptanceTests.cs:150-154` and `:271-274` assert only `count(shipments) > 0`, with no before/after comparison and no other tables. Contrast `M13OperationalKpiRuntimeTests.cs:860,870` (`sourceBefore == SourceCount()`), which is the right pattern. By source inspection the clause holds (`m13_prune_expired_idle` deletes only from `operational_kpi_reports`, FK cascade to members; `20261110010000_M13TenantReportCapacity.cs:52-59`), but the test would not detect a regression that deleted some shipments.
- G13-S19-A07 ("discloses no counts"): `:68` only asserts there is no JSON property named `counts`. The body is `{code,message,correlationId}` (`OperationalKpiEndpoints.cs:66,83`), so there is no leak today, but a `limit: 4` or `live: 4` field would pass.
- To close: capture row counts of shipments, status changes and exceptions before and after; assert the whole error body contains no digits other than the correlation id, or compare the key set exactly.

### F4 (Medium, residual, policy-level): one low-privilege user can hold the whole tenant quota
- The quota is per organization (4), but cleanup before a build deletes only the caller's own session report (`OperationalKpiStore.cs:235-241`) and the actor lock is per user, not per session. One Analyst with four sessions can keep all four slots live for the 10-minute lifetime by refreshing, and every other reader gets 429 `report_tenant_capacity_exceeded`. The accepted test does exactly this with one user and five sessions (`M13TenantCapacityAcceptanceTests.cs:28-35`). The user limiter (6 builds/min) does not prevent it.
- Not a defect against the stated policy (4 per organization). Record it as an accepted risk or add a per-user sub-quota.

### F5 (Low): idle cleanup service has no execution test, an implicit enable switch, and marginal interval compliance
- `OperationalKpiCleanupService` is only exercised indirectly: the tests call `m13_prune_expired_idle` directly. Nothing starts the hosted service, so "5-minute poll, up to 8 calls of 16" (`OperationalKpiCleanupService.cs:16-18`) rests on source reading.
- It is registered by connection-string username `harborops_api` (`Program.cs:42-46`), not by a configuration flag like `M15:EnableDelivery`, `M11:EnableEvaluator`; a runtime login with another name silently never cleans up.
- Policy says maintenance "at most 5 minutes, including idle periods" (`G13_G15_POLICY_DECISIONS_20261110.md`). The loop waits 5 minutes before the first pass (`:27`) and then sleeps 5 minutes after each pass, so the period is 5 minutes plus sweep time. The policy also asks to "alert on lag and backlog"; only a `LogWarning` exists (`:68-69`).
- Throughput bound: 128 deletions per 5 minutes per instance. With every tenant refreshing four reports each 10 minutes, creation outpaces cleanup beyond roughly 64 active tenants; builds also prune 8 per organization, which helps, but no evidence covers a backlog.

### F6 (Low): measurement and sensitivity notes

Materialization is a single `INSERT ... SELECT`, so it would also be consistent under READ COMMITTED; no mutant changes the isolation level. This does not affect the assertions, but the brief's "repeatable-read stability" is not independently demonstrated.

The test itself (40 candidates, exactly 16 then 16 then 8, `M13TenantCapacityAcceptanceTests.cs:238-248`) does prove the cap and the guard separately.

The clause (expired snapshot removed, capacity restored, live ones kept) is still literally witnessed, and identity of the three survivors is checked (`:136-144`).

It proves PostgreSQL discards uncommitted rows, not that `BuildLockedOnceAsync` has no other pre-commit window. `G13AfterReportCommit.log` also contains a `FileNotFoundException` because the substring filter also selected the recovery test; the real recovery run passed.

A database at the base M13 migration but without `20261110010000` (partial deploy or rolling back only the capacity migration) would make the whole GRANT fail. The normal path migrates fully first.
