## 1. Findings, ranked

### Medium
**M1. Unread-count and state-filtered reads are unmeasured at the stated 1,000,000-row limit; likely super-linear cost.**
`m15_user_notifications` RLS calls `m15_can_read` per row (migration `20261109010000_M15ScopedNotifications.cs:270-272`), a VOLATILE plpgsql function that itself calls `m11_read_allowed` (HMAC + key lookup + 4-table join) and an EXISTS join (`:243-265`). `UnreadAsync` does `COUNT(*)` over every unread row (`NotificationStore.cs:191-195`); the web client polls list plus count every 30 s (`NotificationCenter.tsx:77-81`); `CommandTimeout` is 25 s (`NotificationStore.cs:52`). The scale test pages only 10 x 50 rows with `state=All` (`M15ScaleLoadTests.cs:121-139`), prints p50/p95 and never asserts them (`:145-150`), and never calls `/unread-count` or `state=Unread`. Retention deletion is intentionally disabled (P12), so rows only grow. I could not measure this (read-only); it is reasoned from the plan shape. Verify with `EXPLAIN (ANALYZE)` of the count at 100k/1M unread rows before acceptance.

**M2. The 1,000-recipient cap (`PZ015`, `recipient_limit`) has no runtime test; behavior at the cap is a silent permanent stop.**
`:166-181,206` count and reject; the only reference in tests/scripts is a regex in `scripts/check-m15-contract.mjs:36`. At 1,001 eligible members an event retries 5 times with backoff and is quarantined (`:205-215`); nothing re-queues it, the only signal is a log warning (`NotificationDeliveryService.cs:25-28`), and `docs/OPERATIONS.md` has no quarantine runbook. G15-S12-A05 ("bounded admission and pending work") is therefore proven only for the 252-member case.

**M3. Several atomic clauses have no witness that proves them (matrix is scenario-level, not clause-level).** The audit script itself says a scenario-level pass is "a candidate, not proof" (`scripts/audit-g13-g15-assertions.py:3-4`) yet marks these FULLY_TESTED:
- **G15-S01-A05** (M13 independence, notification default-off): witnesses are three outbox/receipt tests. `G13G15FeatureDefaultAcceptanceTests.cs:15-22` asserts only `M10:EnableProjector` and `M11:EnableEvaluator`, not `M15:EnableDelivery`. Default-off exists only as regexes in `check-m15-contract.mjs:58-59,72-73` (which does run in the `contracts` step but is not mapped).
- **G15-S05-A04** (alert visibility grants no mutation/export) and **S18-A05** (a personal action never mutates M11 exception state): no test attempts a mutation/export from a notification-only role or asserts `shipment_exceptions` is unchanged after Acknowledge. Structurally true (the function touches only M15 tables) but unasserted.
- **G15-S12-A03/A04**: "two competing dispatchers" races over **one** outbox row (`M15FanoutLoadTests.cs:88-95`), so SKIP LOCKED partitioning is not exercised; readers run **after** fanout completes (`:106-119` then `:147-159`), not "during fanout".
- **G15-S12-A05**: the "32 concurrent readers" bound is a `SemaphoreSlim` in the test (`:146`), not product admission control.
- **G15-S14-A02/A03**: mapped to `RejectedAuditWriteRollsBack...` (an M11 audit test), not to trigger-failure behavior; no test drives the M11 HTTP evaluate/resolve path with a failing outbox trigger. `FailedOutboxInsertRollsBack...` (`M15NotificationBoundaryTests.cs:93-132`) proves the error propagates (and the mutant that swallows it is killed), but its post-rollback zero counts (`:126-131`) are true by the test's own `RollbackAsync`.
- **G15-S21-A03** (timeouts): no dispatcher timeout/slow-SQL test; PL/pgSQL `EXCEPTION WHEN OTHERS` does not catch `query_canceled` (57014), so a timing-out event never increments `attempt_count` and, because the whole batch is one transaction, blocks the other events in that batch.
- **G15-S21-A05** (HTTP outage): the real test `RealNotificationDatabaseLockReturnsBoundedScopedHttpFailureAndRecovers` is **not listed as a witness for any assertion** in `ASSERTION-MATRIX.csv` (0 hits; it appears only at `verify-g13-g15-evidence.py:508`), and it exercises only `GET list`, not count/detail/PATCH.

### Low
**L1. Mutation set only mutates the M15 SQL.** `scripts/g15-mutation-campaign.py:17-87` has 11 SQL mutants. None touches C# (cursor org/user/session/state binding, 20-minute expiry, limit bounds, `ViewShipmentData` guard, the `organization_id=@org` predicates in `NotificationStore.cs:133-141,170-172`). S24-A01 ("tenant and personal-row predicate mutants") rests on one RLS mutant; S24-A04 has no "audit failure swallowed" mutant (only "audit skipped"). `receipt-cas-bypassed` is killed indirectly: the log shows `Expected: Conflict, Actual: UnprocessableEntity`, i.e. the stale attempt used an already-read receipt, so a CAS-only regression with a valid transition would not be distinguished.
**L2. Kill verdict is looser than "right reason".** `g15-mutation-campaign.py:197` calls a mutant KILLED if the exit code is non-zero, the target name appears in the output and "Failed " appears anywhere. I did not rely on it: I read all 11 mutant logs and each fails at the intended assertion (see Q2).
**L3. Crash windows are partly surrogate.** `G15BeforeHistoryCommit` (`G13G15CrashRecoveryTests.cs:155-170`) and `G15BeforeClaimCommit` (`:325-335`) hold a raw admin-connection transaction, not the API/evaluator or the production claim function; `G15Before/AfterFanoutCommit` call `m15_deliver_pending` directly with a hand-signed scope (`:239-281`). Only `AfterReceiptCommit` and `AfterResponseDiscarded` kill a real in-process API. No kill occurs *during* function execution. The PostgreSQL semantics make the surrogate results valid, but "kill the API process" is not literally what is shown. `:374` compares two consecutive reads of the same count (tautological).
**L4. Late-delivered events and cursor cutoffs.** `created_at_utc` of a receipt is the M11 history time, not delivery time (`m15_deliver_pending` insert `:186-188`). An event delivered after an old cursor's cutoff but timestamped before it can appear on later pages or be skipped relative to the keyset position; the cutoff test only inserts events *after* the cutoff (`M15FinalAuthorizationTests.cs:183-197`). Retry backoff up to 8 minutes makes this reachable.
**L5. 100-reader and 1M tests are narrower than their names.** 100 reads are the same user and session through `NotificationStore` (no HTTP, no rate limiter) with `limit=1` (`M15FanoutLoadTests.cs:147-159`), asserting a single distinct id; the 1M test seeds 1,000,000 receipts for one recipient by direct SQL, bypassing the dispatcher (`M15ScaleLoadTests.cs:85-105`). They prove index/paging, not multi-recipient isolation under load.
**L6. Single-batch head-of-line and 40001 handling.** A serialization failure returns 0 (`NotificationStore.cs:265-270`), so the service sleeps 15 s (`NotificationDeliveryService.cs:31-32`) although work is pending.
**L7. Local-mode job results are self-reported.** `verify-g13-g15-evidence.py:46-58` derives `success` from exit codes in the orchestrator's own `commands.tsv`. I cross-checked against TRX/logs and they agree, but nothing external attests the runs.

### Informational (no action needed to close G15)
- Security design is strong: HMAC-scoped, session-bound, transaction-local read scope (`m11_read_allowed` reuse), `SECURITY DEFINER` functions with fixed `search_path`, `REVOKE ALL` from `harborops_api`/`harborops_worker` on all three tables plus SELECT-only on receipts (`AuditRoleProvisioner.cs` m15 block), RLS on all three tables, FOR SHARE/FOR UPDATE ordering consistent with M2, replay bound to org/user/key/session/action/version, generic 404 for foreign vs unknown ids, no PII in fixed titles, audit metadata only `{"action":"Acknowledge"}`.
- `G13G15RevocationAcceptanceTests` (11 revocation causes plus a lock-queued revocation race) and the forged-scope SQL tests are genuinely good witnesses.

**Q3. Is the default-registered `OperationalKpiCleanupService` inside the intended boundary, and distinct from the disabled P12 cleanup?** **Yes to both, with one condition.**

- Policy basis: the recorded G13 operating targets require "expired-report maintenance at most 5 minutes including idle periods" (`G13_G15_POLICY_DECISIONS_20261110.md`, targets table). P12's "no deletion / background cleanup" language applies to notification rows, immutable history, intents, replays and audit. Different tables, function, caller and policy. So it is within the intended boundary **if "no deletion jobs" is read as the P12 retention scope**; read literally as "no deletion anywhere", it is a deletion job and the owner must say so explicitly.
- P12 is "disabled" because the code does not exist: nothing in `src/.../Notifications/` or the M15 migration deletes (grep `DELETE FROM|ExecuteDelete` = no hits), and `harborops_api` has no DELETE on any M15 table (REVOKE ALL). That is the strongest possible form of disabled. No test asserts that M13 cleanup leaves M15 rows intact; the guarantee is structural.
- Condition: registration is unconditional when the login is `harborops_api` (`Program.cs:43-46`); there is no config flag, unlike M15 delivery (`:53`) and M10/M11. Recommend a documented kill-switch or record explicitly that default-on is intended.
