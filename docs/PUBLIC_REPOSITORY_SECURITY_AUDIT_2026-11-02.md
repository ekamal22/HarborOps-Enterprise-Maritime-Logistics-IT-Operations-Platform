# Public Repository Security and Disclosure Review

**Review date:** 2026-11-02
**Reviewed `main` SHA:** `1bec9b1b55392da7269236dfbd7d07e456fef52b`
**Publication decision:** NOT CLEARED. The existing repository must remain private until the outstanding public-source disclosure checks are completed.
**Deployment decision:** NOT CLEARED for internet-facing authentication or production hosting. Source-code publication and operating a public server are separate decisions.

## Scope and method

This was a remote, read-only repository source and metadata audit. It did not execute application code, launch a penetration test, contact a production deployment, perform a live CVE refresh or change repository settings.

- Inspected the full `main` tracked-file tree: 318 textual files at the reviewed SHA. Applied high-confidence pattern matching for PEM private-key delimiters, common cloud/provider token formats, credential-bearing database URLs and email domains. Inspected configuration, workflows, application authentication, reverse proxy, Docker Compose, documentation and M6/G6 security records.
- Inspected tracked filenames across all 10 branch tips. No committed `.env`, PEM/PFX key, database dump, backup, executable evidence ZIP or obvious credentials file was found at those tips. `.env.example` is a placeholder, not a production secret.
- Compared branch ancestry with `main`. Three branches retain divergent, unmerged history: `docs/product-delivery-source-of-truth` (100 commits ahead), `feat/m0-engineering-baseline` (63 ahead), and `fix/m0-net10-postgres-browser-hardening` (168 ahead). These counts are compare results relative to the reviewed `main` SHA, not a count of unique historical secrets.
- Reviewed 62 distinct branch-tip blob versions absent from `main` across those three branch tips using the same high-confidence patterns. The other seven branch tips are ancestors of `main` at the reviewed revision.
- Reviewed commit author, committer and message metadata for 492 commits reachable from `main`. Author/committer email domains in that set were GitHub no-reply or GitHub service domains.
- Current-file email literals found by this scan use synthetic `example.test` and `host.test` domains. No high-confidence private key, provider token or credentialed database URI matched in the 318 current files or 62 additional branch-tip blobs.

**Important limitations:** Regex-based scans are not comprehensive secret detection. Credentials with unfamiliar formats, generic passwords, encoded material or high-entropy secrets could go undetected. The contents of **all historical Git blobs** (including deleted and orphaned objects, pull request refs and every intermediate commit) have not been scanned. Historical Actions run logs and artifacts were not downloaded or reviewed. Permission-restricted GitHub security-alert and repository-admin settings were not inspected. The scan of current branch tips is not a full-history scan. These limitations block a definitive statement that publication is safe.

## Positive controls confirmed in current source

- `.gitignore` excludes local `.env`, private `secrets.json` and key material; `.env.example` contains an obvious placeholder database password.
- `compose.yaml` exposes PostgreSQL, API and web only on `127.0.0.1` in the accepted local configuration.
- Cookie handling is HTTP-only and SameSite Strict, the default non-local policy requires Secure cookies, and the authentication system performs session validation. PostgreSQL-backed tenant authorization and CSRF controls have dedicated tests.
- G6 includes role/session/tenant mutation controls, three browser engines, dependency and image scans, outage/recovery, and source-locked raw evidence. G6 acceptance is **not** a public-hosting security certification.
- No root `LICENSE` or sensitive-looking tracked binary backup/key filename was present at the audited `main` revision. Filename and pattern checks are evidence of absence of matches only, not proof of absence of secrets.

## Required publication gate for the existing repository

1. Inspect all refs and historical objects with a local full-history secret scanner and review actual findings manually. Include the three divergent branch histories, deleted files, PR refs, tags, and reachable objects not present in current trees. Preserve a sanitized full-coverage report and note any unreachable objects that require separate inspection.
2. Inspect existing and historical GitHub Actions logs, downloadable artifacts, workflow inputs and retained metadata. Confirm that secrets, account information, confidential data and machine-specific sensitive output are absent. If GitHub API access is insufficient, complete this in GitHub's web UI or an authorized local export; do not mark it passed by assumption.
3. Disable automatic Actions execution before changing repository visibility, while the hosted CI prohibition remains. Confirm settings, workflows and absence of newly triggered runs.
4. Review older branches and documents for sensitive organizational, third-party, personal or employment information independent of secret scanners. If history cleanup is required, coordinate explicit approval, protect accepted evidence, and rotate any exposed secrets before rewriting or deleting anything.
5. Refresh dependency and container scans with current advisory feeds locally. Recheck exact source/image hashes and zero unresolved findings at the approved severity threshold.
6. Decide whether full historical development records should be shown to viewers. A curated, separately reviewed public snapshot provides a simpler approval path and avoids publishing private development history.
7. Record final source SHA, refs reviewed, scanner versions, retained evidence and an explicit publication decision. Keep the repository private until that decision is recorded.

For a future internet-facing deployment, HOST-01 and HOST-02 must be remediated and independently verified before exposure. Publication of a source-only portfolio and deployment approval must never be conflated.

## Execution boundary

This review only documents risks. It did not modify runtime or workflow code, enable Actions, change repository visibility, download or expose credentials, scan a production system, remove branches, rewrite history, or certify public deployment. Future verification should use the approved E:-backed local environment and avoid creating persistent project data on C:. Preserve current acceptance and evidence records.
