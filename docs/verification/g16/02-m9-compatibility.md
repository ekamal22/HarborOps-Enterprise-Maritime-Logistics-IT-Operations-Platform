# G16 Phase F: M9 compatibility review (read only)

**Method:** `git diff` and legacy `git merge-tree` text analysis between `origin/feat/m9-worker-reconciliation` (`cff7c25`) and M16 `ef08d7c`. Common base is `main` `7b9e19d`. No branch was merged, no combined revision, branch or worktree was created and M9 was not modified. Classifications: **Definite** (observed in the sources), **Probable** (follows from the sources, needs a combined run to prove), **Needs combined verification**.

| # | Area | Observation | Class |
| --- | --- | --- | --- |
| 1 | Textual conflicts | Both branches edit `Program.cs`, `OrganizationPolicy.cs`, `HarborOpsDbContext.cs`, `HarborOpsDbContextModelSnapshot.cs`, `ReferenceHistoricalUpgradeTests.cs`, `TrackingInboxMigrationTests.cs` and nine shared documents. The legacy merge-tree reports `changed in both` for all of them. `OrganizationPermission` is one enum line that both branches extend. | Definite |
| 2 | Migration order | M16 is `20261104180000_AuditEntries`, M9 is `20261104190000_TrackingWorker`. Neither lists the other as a parent; EF orders by id so M16 would run first. Each branch's snapshot lacks the other's entities, so a combined snapshot must be regenerated and `MigrationSnapshotTests` rerun. | Definite (ordering), needs combined verification (snapshot parity) |
| 3 | Hard-coded migration counts | Both branches change the expected applied-migration count in `ReferenceHistoricalUpgradeTests` and `TrackingInboxMigrationTests` from 9 to 10. Git would merge those lines cleanly, but the combined head has 11 migrations, so the merged tests would fail or assert the wrong head. | Definite (silent semantic conflict) |
| 4 | Worker grants | `AuditRoleProvisioner` grants `harborops_worker` INSERT and SELECT on `tracking_work_attempt_events` when M9 tables exist. M9's own role script (`scripts/m9-worker-role.sql`) explicitly revokes INSERT, UPDATE and DELETE on that table so attempts are written only by the SECURITY DEFINER trigger `m9_log_work_transition`. In a combined run the M16 provisioner (last step of `--migrate`) would give the worker direct INSERT into M9's immutable attempt log. | Definite (contract contradiction); exploitability needs combined verification |
| 5 | Role ownership | Both create `harborops_worker`. M16 provisions it automatically with a password from `AuditRoles__WorkerPassword`; M9 expects a manual role script and a `\password` step. Two provisioning paths with different grant sets must be reduced to one. M9's guard `m9_guard_work_item` keys on `session_user = 'harborops_worker'`, which matches the name M16 creates. | Probable |
| 6 | Column grants | M16 and M9 list the same UPDATE column set on `tracking_inbox_work_items` for the worker (state, attempt_count, lease fields, redrive generation, error code, completion, resolution, updated time). | Compatible on inspection |
| 7 | API role and M9 tables | The API role gets `SELECT ON ALL TABLES` and UPDATE/INSERT on `tracking_inbox_work_items`. M9 redrive runs through the API and relies on SECURITY DEFINER triggers for attempt events, so no extra API grant is apparent. The grants must be re-evaluated because the provisioner runs only at migration time. | Needs combined verification |
| 8 | Audit coverage | M16 capture triggers cover 15 tables and exclude M8 receipts. M9 adds `tracking_work_attempt_events`, `tracking_processing_effects` and work-item state transitions, none audited by M16. M9 keeps its own immutable attempt log. Whether M16-D03 requires audit rows for worker effects is undecided in the documents. | Needs decision and combined verification |
| 9 | Lock ordering | M16 audit rows reference `organizations(id)` (see G16-F002). M9 work-item updates and `m9_lock_active_organization` also take organization-level locks. The deadlock mechanism found in M16 alone applies to any M9 writer path that updates an audited table after another transaction holds the organization row. | Probable |
| 10 | Triggers | M9 `m9_work_guard` (BEFORE INSERT, UPDATE, DELETE), `m9_work_transition_audit`, `m9_work_effect_required` and `m9_effect_terminal` are on tables that M16 does not trigger. No trigger name or table overlap was found. | Compatible on inspection |
| 11 | Runner and Compose | M16 owns `compose.g16.verify.yaml` with no worker service; M9 owns `scripts/verify-m9-local.sh`. A combined verification needs a worker identity and grants in the Compose stack. | Needs combined verification |
