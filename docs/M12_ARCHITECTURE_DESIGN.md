## Implemented interfaces

- `GET /api/v1/organizations/{organizationId}/shipments/search`: `q` (80-char trimmed case-insensitive substring), `recordStatus` (Active default/Archived/All), `workflowStatus`, `voyageId`, `originPortId`, `destinationPortId`, and paired explicit UTC `plannedDepartureFromUtc`/`plannedDepartureBeforeUtc`, `plannedArrivalFromUtc`/`plannedArrivalBeforeUtc`. Paired windows use inclusive start/exclusive end, at most 366 days. All filters combine with AND. Unknown, repeated and invalid parameters are denied.
- M6 voyage matching uses a tenant-scoped EXISTS on the association interval containing `asOfUtc`. No inferred ETA, voyage movement or container boarding.
- Search `limit` 1..100 (default25); all encoded query strings are bounded to 4,096 characters, SQL statements to 15 seconds and the scoped search store operation to 25 seconds after authentication middleware, below the 30-second API proxy read timeout. response `{shipments,nextCursor,asOfUtc}`. Stable UUID ascending keyset. Cursor protected with the existing persisted ASP.NET Data Protection key ring, 15-minute TTL, bound to tenant, authenticated actor, active login session, filters and reference instant. Later pages are live reads, not a transaction-spanning snapshot. Accepted M5 list and detail routes remain unchanged.
- `GET /api/v1/organizations/{organizationId}/exports/shipments`: same business filters, no paging. `ExportShipmentData` allows only Analyst/Manager, not Auditor, Administrator or Support. The API rejects cross-origin browser downloads, executes one tenant-scoped repeatable-read transaction, materializes at most 5,001 rows, rejects more than 5,000 or 10MiB without partial download, applies a 25-second internal preparation budget (below the accepted Nginx 30-second read timeout) and 15-second per-statement limit, then records a required signed, restricted export-preparation audit event before committing.
- CSV v1 fixed columns: Shipment ID, Reference Code, External Reference, Display Name, Workflow Status, Record Status, Origin Port ID, Destination Port ID, Planned Departure UTC, Planned Arrival UTC, Created UTC, Updated UTC. UTF-8, quoted fields, CRLF, doubled embedded quotes, spreadsheet-formula apostrophe defense. No raw tracking, credentials, M16 audit data or unapproved M11 evidence. Per-principal rate limit 10/min and single in-flight export per API instance. `Content-Disposition` attachment; no-store, nosniff.
- SQL-only EF migration `20261107230000_M12ShipmentExportAudit` creates `m12_record_shipment_export`, a SECURITY DEFINER function, the restricted `m12_export_proof_keys` verifier table and unique event/correlation index. A short-lived HMAC-SHA256 proof issued only by the HTTP runtime binds organization, actor, session, filter digest, row count, byte count, correlation and expiry. The function checks the proof against a migrator-provisioned key, then revalidates active scope and inserts `shipment.export_prepared`. Replay of the same signed correlation fails. Its `Down` migration refuses to remove audit controls if any export-preparation audit history exists. No accepted migration 1..13 was rewritten. The proof protects against database-only SQL forgery within the accepted runtime trust boundary; it is not a cryptographic digest of the response bytes and does not prove browser receipt.

## Frontend and M11 boundary

`ShipmentWorkspace.tsx` preserves M5 local drafts and detail selection while using typed advanced filters and protected pagination; canManage Analyst/Manager sees CSV controls, Auditor does not. Session/organization changes unmount protected state and abort pending export requests.

M11 implementation draft PR #31 exists separately from planning draft PR #30. M11's `20261107180000_ShipmentExceptions` and M12's `20261107230000_M12ShipmentExportAudit` have **distinct** migration IDs, but each is the fourteenth migration on its isolated branch. Combined integration would discover both in timestamp order and must update exact-count migration tests, M11 EF model snapshot, runtime role provisioning, API registration, shared UI, docs and test fixtures on one combined SHA. M12 neither implements nor consumes unaccepted exception rules. The accepted M9 ARRI/DEPA hold, 10,000 unresolved-work cap, default-off M10 projector and null ETA remain unchanged.

**Security configuration:** A separate 32-byte base64 key, `HARBOROPS_M12_EXPORT_PROOF_KEY`, is wired only to migrator and API as `M12ExportProof__Key`. The Compose variable is optional so unrelated accepted-stack checks still start, but an unset key makes CSV export return sanitized 503. Malformed configured keys fail privileged provisioning. Never store, log or commit the secret. See [correctness audit](M12_CORRECTNESS_AUDIT_20261107.md).
