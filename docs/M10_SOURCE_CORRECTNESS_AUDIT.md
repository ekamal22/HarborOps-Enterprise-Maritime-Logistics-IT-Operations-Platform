# M10 Source Correctness Audit

**Date:** 2026-11-05  
**Audited revision:** `83d78bb7b271b96d5086044801fc503f07d8a417` on `feat/m10-timeline-projections`, PR #23.  
**Accepted baseline:** G9 on `main` at `b4f7b93f1ee8135b9a16b605ded315b3fbc036cc`.  
**Disposition:** **BLOCK MERGE AND G10 ACCEPTANCE.** Runtime code was not changed during this review.  
**Review type:** Independent static source and contract review. No compile, migration, PostgreSQL, web/browser, failure-injection or security campaign was run. Findings below are code-supported risks and discrepancies, not reproduced runtime incidents.

## Review basis

Reviewed the M10 domain reducer, migration, SQL-backed store, HTTP endpoints, hosted projector, shipment UI, local verification helper, new tests and changed migration tests. Compared relevant behavior with accepted M8/M9 receipt/effect persistence and the proposed M10 architecture and G10-S01 through G10-S25 matrix in open PR #22. That planning PR is not a frozen M10-local contract.

## High severity: blocking correctness and integrity

| ID | Code location | Finding and consequence | Required correction |
| --- | --- | --- | --- |
| M10-C01 | `ShipmentTimelineStore.cs`, `MaximumEvents` and `LoadAsync` (about lines 25, 50-87) | A shipment with more than 10,000 **resolved** events throws `TrackingTimelineLimitException`. `ReadAsync`, `PersistAsync`, the two GET endpoints, correction and rebuild all depend on this same loader. M9's 10,000-item cap applies to **unresolved** work, not total historical events. One long-lived shipment can permanently lose all M10 operations without any M9 cap breach. Repeated projector scans may fail on that shipment and leave other backlog work delayed. | Build bounded keyset timeline reads independently of a complete-history projection reducer. Provide resumable, resource-bounded streaming/chunked rebuild or an equivalent verified historical aggregation strategy. Stress test more than 10,000 resolved events, including corrected events. |
| M10-C02 | `20261105180000_ShipmentTrackingProjections.cs`, `shipment_projection_applications` (about lines 74-85) | `receipt_id` references an M9 effect and `(organization_id,shipment_id)` references a shipment, but the database does not ensure that **the effect belongs to that same organization and shipment**. Direct SQL can persist a foreign or mismatched receipt/shipment application, violating the stated cross-tenant integrity requirement. Current application SQL normally inserts correctly, but the invariant is not enforced at the database boundary. | Introduce a suitable composite unique key on M9 effect identity and a matching composite FK on the application table, or an equally strong immutable, tenant-safe database validation. Add negative direct SQL and concurrency tests. |
| M10-C03 | `ShipmentTimelineStore.cs`, `PersistAsync` and `DirtyAsync` (about lines 180-226, 329-355) | A projector scan is driven by missing application rows or a missing/old projection policy. Existing `shipment_projection_applications` rows are inserted with `ON CONFLICT DO NOTHING` and never updated when a policy is revised. After a projection policy changes, the projector can update the projection while leaving all application evidence at the old policy; the dirty query will then stop selecting it. Additionally, correction-related or independently repaired projection drift with all application rows present is not discoverable by this scan. | Define receipt-plus-policy application identity or atomic versioned reconciliation; use a reliable correction-generation/digest dirty signal and test policy upgrade, correction, crash recovery and deliberate derived-row corruption. |
| M10-C04 | `20261105180000_ShipmentTrackingProjections.cs`, `m10_validate_correction` (about lines 88-116) | The append-only trigger checks correction-chain conflicts with ordinary `EXISTS` queries, but does not serialize concurrent **direct SQL** writers. Concurrent non-API inserts can each miss the other's uncommitted row and create a correction cycle or forbidden chain despite different target/generation uniqueness values. API writes serialize on the shipment row, but the documented database invariant is expected to survive direct SQL as well. This is a source-identified race requiring PostgreSQL reproduction. | Acquire the same scoped lock inside the database guard, or enforce the invariant using a serialized correction procedure and database privileges that forbid direct inserts. Run two-transaction cycle/chain adversarial tests. |
| M10-C05 | `20261105180000_ShipmentTrackingProjections.cs`, `Down` (about lines 139-150) | M10 migration rollback unconditionally drops the append-only correction history and projection-application records. Unlike accepted M9's downgrade guard, there is no refusal when source-linked M10 evidence exists. A downgrade can destroy correction provenance that was intended to remain immutable. | Refuse downgrade when any correction or other retained source-linked evidence exists, subject to an explicitly approved retention/migration policy. Test downgrade with populated data and ensure historical records survive failed rollback. |

## Medium severity: behavioral and contract correctness

| ID | Code location | Finding and consequence | Required correction |
| --- | --- | --- | --- |
| M10-C06 | `ShipmentTimelineStore.cs` `LoadAsync` ORDER BY, `TrackingTimelinePolicy.cs` `Order` | SQL orders source event keys using the database collation, while the reducer uses `StringComparer.Ordinal`. Valid M7 source keys include mixed-case characters. A non-binary database collation can return timeline pages in an order that differs from the reducer and from the specified canonical order. | Enforce identical byte/ordinal ordering at both boundaries or sort a stable snapshot with the reducer's comparer before any cursor slice. Test mixed-case, timestamp and source tie breakers on real PostgreSQL. |
| M10-C07 | `TrackingTimelinePolicy.cs`, `ShipmentTimelineEvent` / `Reduce` (about lines 6-60) | The observed `EquipmentIn/EquipmentOut` state is derived from the last event across **all containers on a shipment**, but the M9 effect's `ContainerId` is discarded when building timeline rows. For a multi-container shipment, the latest event from one container can misleadingly stand for the entire shipment; simultaneous distinct-container observations can be labeled a conflict without being contradictory. | Preserve equipment/container provenance in the timeline and define an explicit per-container observation and shipment-level aggregation policy before approval of M10-01. Add two-container ordering/conflict tests. |
| M10-C08 | `ShipmentTimelineEndpoints.cs` `GET /tracking-projection` (about lines 140-160) | The response returns the full `inputDigest` even though proposed G10-S14 requires no digest exposure in HTTP payloads. The architecture permits a digest identifier, not necessarily the raw canonical fingerprint. | Remove the raw digest from the public response, or freeze and explicitly approve a privacy-reviewed opaque identifier. Add API redaction assertions for both GET endpoints. |
| M10-C09 | `ShipmentTimelineEndpoints.cs` POST mutations and `ShipmentTimelineStore.cs` generation comparison | Neither mutation has a request idempotency key or a bounded endpoint-specific rate policy. After an ambiguous successful correction COMMIT, retrying the same request with the same expected generation returns a conflict with no durable idempotent replay response. Rebuild requests also load the whole history. | Specify and persist scoped mutation idempotency identities, return stable replay results and add bounded mutation rate/concurrency controls. Test interrupted responses and repeated requests. |
| M10-C10 | `TrackingProjectionHostedService.cs`, `Program.cs`, `compose.g10.verify.yaml` | The optional background projector runs under the API process's database identity, and the G10 verification Compose profile enables it using the main API connection with broad database privileges. This differs from the least-privilege separation established for M9 worker processing. | Define a restricted projector DB role/connection, verify minimum privileges, enforce explicit opt-in, and test that the projector cannot alter immutable M8/M9 history or arbitrary tenant records. |
| M10-C11 | `ShipmentTrackingTimeline.tsx` | The UI independently fetches projection and timeline endpoints concurrently. They may observe different database snapshots when a new effect or correction commits between the two requests, producing a temporarily inconsistent displayed state and history. | Return or compare one scope-bound snapshot/revision token for both views, or treat mismatch as stale and refresh atomically. Test concurrent late arrivals and tenant switching. |

## Correctly preserved boundaries observed in source

- M8 accepted receipt/event tables and M9 effect/fencing/worker code are not edited by the M10 source branch.
- The M10 timeline filters on M9-resolved same-organization shipment effects rather than guessing references for parked transport events.
- M5 manual workflow state and history are separate from derived tracking observations; ETA remains unavailable under the accepted source profile.
- The HTTP read routes require selected-organization shipment-read permission. Correction/rebuild routes require Manager role, CSRF/Origin validation and additional transactional session/membership checks.
- The projector is disabled by default; source changes do not authorize public deployment or lifting the G9 backlog hold.

## Prioritized remediation sequence

1. Resolve M10-C01 and M10-C02 first. The full-history limit and missing composite effect scope are major acceptance blockers.
2. Correct M10-C03, C04 and C05 with real PostgreSQL negative/race/retention tests.
3. Freeze the M10-01 multi-container, ordering, API redaction and idempotency decisions, then fix C06 through C11 and expand focused tests.
4. Run a clean build and migrations locally on E:, correct all compiler/runtime findings, rerun all affected G0-G9 regressions and the full G10-S01 through G10-S25 matrix on the final SHA. Preserve every failed attempt and source hash.
5. Obtain independent raw-evidence reconciliation and explicit G10 acceptance before any merge. Do not enable GitHub Actions or modify retained historical evidence.

**Audit result:** No runtime success claims. A source-level correctness audit does not authorize G10 acceptance or merge.
